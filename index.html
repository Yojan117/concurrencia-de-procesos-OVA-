Introducción

Un proceso es un programa en ejecución, con su propio espacio de direcciones, registros y estado. Los sistemas operativos modernos ejecutan muchos procesos a la vez; incluso con una sola CPU, el S. O. cambia rápidamente de uno a otro para dar la ilusión de simultaneidad.

La concurrencia es la capacidad del sistema de tener varios procesos (o hilos) en progreso durante el mismo período. Aporta mejor uso de la CPU y tiempos de respuesta más cortos, pero introduce un riesgo: cuando los procesos comparten recursos, el resultado puede depender del orden en que se intercalan sus instrucciones.

Introduction

A process is a running program, with its own address space, registers and state. Modern operating systems run many processes at once; even with a single CPU, the OS switches quickly between them to give the illusion of simultaneity.

Concurrency is the system’s ability to keep several processes (or threads) in progress during the same period. It improves CPU usage and response times, but it brings a risk: when processes share resources, the result may depend on the order in which their instructions are interleaved.

Concurrencia

Varias tareas están en progreso a la vez, aunque no se ejecuten en el mismo instante. En una CPU de un núcleo se logra con multiprogramación y cambios de contexto.

Paralelismo

Varias tareas se ejecutan realmente al mismo tiempo en distintos núcleos o procesadores. Todo programa paralelo es concurrente, pero no al revés.

Concurrency

Several tasks are in progress at once, even if they do not run at the same instant. On a single-core CPU it is achieved with multiprogramming and context switches.

Parallelism

Several tasks run truly at the same time on different cores or processors. Every parallel program is concurrent, but not the other way around.

El planificador decide qué proceso listo usa la CPU y por cuánto tiempo (quantum). En el cambio de contexto el S. O. guarda los registros y el contador de programa del proceso saliente en su bloque de control de proceso (PCB) y carga los del entrante.

Como el cambio puede ocurrir entre cualquier par de instrucciones, el programador no controla el orden de ejecución, y de ahí nacen los problemas de la siguiente sección.

The scheduler decides which ready process uses the CPU and for how long (the quantum). In a context switch the OS saves the outgoing process’s registers and program counter in its process control block (PCB) and loads the incoming one’s.

Since the switch can happen between any two instructions, the programmer does not control the execution order, and that is where the problems of the next section come from.

Condiciones de carreraRace conditions

Una condición de carrera ocurre cuando dos o más procesos acceden a datos compartidos y el resultado depende del orden exacto en que se ejecutan. Ejemplo clásico: dos procesos incrementan la misma variable x. En lenguaje máquina, x = x + 1 son tres pasos:

LOAD  reg, x      ; leer x en un registro
INC   reg         ; sumar 1
STORE x, reg      ; escribir el resultado en x

Si el S. O. interrumpe a un proceso justo después del LOAD y deja correr al otro, ambos leen el mismo valor y uno de los incrementos se pierde (actualización perdida).

Idea clave: el problema no es que los procesos corran a la vez, sino que el orden de sus instrucciones intercaladas cambia el resultado.

A race condition happens when two or more processes access shared data and the result depends on the exact order in which they run. Classic example: two processes increment the same variable x. In machine language, x = x + 1 takes three steps:

LOAD  reg, x      ; read x into a register
INC   reg         ; add 1
STORE x, reg      ; write the result back to x

If the OS interrupts one process right after the LOAD and lets the other run, both read the same value and one increment is lost (a lost update).

Key idea: the problem is not that processes run at once, but that the order of their interleaved instructions changes the result.

La sección crítica es el fragmento de código que accede al recurso compartido. Una solución correcta debe cumplir:

  • Exclusión mutua: nunca dos procesos dentro de su sección crítica al mismo tiempo.
  • Progreso: si nadie está en la sección crítica, la decisión de quién entra no se pospone indefinidamente.
  • Espera acotada: ningún proceso espera para siempre (sin inanición).
  • No suponer nada sobre la velocidad ni el número de CPU.
do {
    entrar_SC();      // protocolo de entrada
    /* sección crítica */
    salir_SC();       // protocolo de salida
    /* sección restante */
} while (true);

The critical section is the code segment that accesses the shared resource. A correct solution must satisfy:

  • Mutual exclusion: never two processes inside their critical section at the same time.
  • Progress: if nobody is in the critical section, the decision of who enters is not postponed indefinitely.
  • Bounded waiting: no process waits forever (no starvation).
  • No assumptions about CPU speed or number of CPUs.
do {
    enter_CS();       // entry protocol
    /* critical section */
    exit_CS();        // exit protocol
    /* remainder section */
} while (true);

SincronizaciónSynchronization

Solución por software para dos procesos (0 y 1), con un arreglo quiere[2] y una variable turno:

// Proceso i (el otro es j = 1 - i)
quiere[i] = true;
turno = j;
while (quiere[j] && turno == j) ;   // espera activa
/* sección crítica */
quiere[i] = false;

Cumple las tres condiciones, pero gasta CPU esperando y, en hardware moderno, requiere barreras de memoria para funcionar bien.

A software solution for two processes (0 and 1), using an array wants[2] and a variable turn:

// Process i (the other is j = 1 - i)
wants[i] = true;
turn = j;
while (wants[j] && turn == j) ;    // busy waiting
/* critical section */
wants[i] = false;

It meets the three conditions, but it wastes CPU while waiting and, on modern hardware, needs memory barriers to work properly.

Instrucciones atómicas como test-and-set o compare-and-swap leen y modifican una variable sin que nadie pueda interrumpir en medio. Con ellas se construyen los cerrojos (spinlocks).

Desactivar interrupciones sirve dentro del núcleo en una sola CPU, pero no es viable para procesos de usuario ni en multiprocesadores.

Atomic instructions such as test-and-set or compare-and-swap read and modify a variable with no chance of being interrupted in between. They are the building blocks of locks (spinlocks).

Disabling interrupts works inside the kernel on a single CPU, but it is not viable for user processes or on multiprocessors.

Propuestos por Dijkstra: una variable entera protegida, accesible solo mediante dos operaciones atómicas.

wait(S)   // P:  S = S - 1; si S < 0, el proceso se bloquea
signal(S) // V:  S = S + 1; si S <= 0, se despierta a un proceso

Un semáforo binario (mutex) vale 0 o 1 y da exclusión mutua; un semáforo contador controla el acceso a un conjunto de recursos idénticos. A diferencia de la espera activa, el proceso se bloquea y no consume CPU hasta que lo despiertan.

semaforo mutex = 1;
wait(mutex);
   /* sección crítica */
signal(mutex);

Proposed by Dijkstra: a protected integer variable, accessible only through two atomic operations.

wait(S)   // P:  S = S - 1; if S < 0, the process blocks
signal(S) // V:  S = S + 1; if S <= 0, a process is woken up

A binary semaphore (mutex) is 0 or 1 and provides mutual exclusion; a counting semaphore controls access to a set of identical resources. Unlike busy waiting, the process blocks and uses no CPU until it is woken up.

semaphore mutex = 1;
wait(mutex);
   /* critical section */
signal(mutex);

Construcción de lenguaje de más alto nivel: agrupa datos compartidos y los procedimientos que los manipulan, y garantiza que solo un proceso a la vez esté activo dentro del monitor. Para esperar condiciones usa variables de condición con wait y signal. Java (synchronized) y otros lenguajes lo ofrecen.

A higher-level language construct: it groups shared data and the procedures that manipulate it, and guarantees that only one process at a time is active inside the monitor. To wait for conditions it uses condition variables with wait and signal. Java (synchronized) and other languages offer it.

Problemas clásicosClassic problems

Un productor deposita elementos en un buffer de tamaño fijo y un consumidor los retira. Hay que impedir que el productor escriba con el buffer lleno y que el consumidor lea con el buffer vacío, además de proteger el acceso al buffer.

semaforo mutex = 1, vacios = N, llenos = 0;

productor:                 consumidor:
  wait(vacios);              wait(llenos);
  wait(mutex);               wait(mutex);
  insertar(item);            item = retirar();
  signal(mutex);             signal(mutex);
  signal(llenos);            signal(vacios);

A producer puts items into a fixed-size buffer and a consumer removes them. We must prevent the producer from writing into a full buffer and the consumer from reading from an empty one, and also protect access to the buffer.

semaphore mutex = 1, empty = N, full = 0;

producer:                  consumer:
  wait(empty);               wait(full);
  wait(mutex);               wait(mutex);
  insert(item);              item = remove();
  signal(mutex);             signal(mutex);
  signal(full);              signal(empty);

Varios lectores pueden leer a la vez, pero un escritor necesita acceso exclusivo. Según la política se puede dar prioridad a lectores (con riesgo de inanición de escritores) o a escritores.

Several readers may read at once, but a writer needs exclusive access. Depending on the policy, priority can go to readers (risking writer starvation) or to writers.

Cinco filósofos piensan y comen en una mesa redonda con cinco tenedores; para comer necesitan los dos tenedores que los rodean. Si todos toman primero el tenedor izquierdo, ninguno consigue el derecho y todos esperan para siempre: es un interbloqueo.

Se evita, por ejemplo, permitiendo solo cuatro filósofos a la vez en la mesa o haciendo que uno tome los tenedores en orden inverso.

Five philosophers think and eat at a round table with five forks; to eat they need the two forks next to them. If everyone picks up the left fork first, nobody gets the right one and all wait forever: a deadlock.

It can be avoided, for example, by allowing only four philosophers at the table at once or by making one of them pick the forks in reverse order.

InterbloqueoDeadlock

Un conjunto de procesos está en interbloqueo cuando cada uno espera un recurso que tiene otro del conjunto, y ninguno puede avanzar. Ocurre solo si se cumplen a la vez cuatro condiciones:

  1. Exclusión mutua: el recurso no se puede compartir.
  2. Retención y espera: un proceso retiene recursos mientras pide otros.
  3. Sin expropiación: los recursos no se pueden quitar a la fuerza.
  4. Espera circular: existe una cadena cerrada de procesos, cada uno esperando al siguiente.

A set of processes is in deadlock when each one waits for a resource held by another in the set, and none can progress. It happens only if four conditions hold at the same time:

  1. Mutual exclusion: the resource cannot be shared.
  2. Hold and wait: a process holds resources while requesting others.
  3. No preemption: resources cannot be forcibly taken away.
  4. Circular wait: there is a closed chain of processes, each waiting for the next.

Prevención

Eliminar una de las cuatro condiciones, por ejemplo pidiendo todos los recursos de una vez o numerándolos y solicitándolos en orden.

Evitación

Conceder un recurso solo si el sistema sigue en «estado seguro» (algoritmo del banquero de Dijkstra).

Detección y recuperación

Permitir el interbloqueo, detectarlo con un grafo de asignación de recursos y romperlo terminando procesos o expropiando recursos.

Ignorarlo

El «algoritmo del avestruz», usado por muchos S. O. de propósito general porque el interbloqueo es raro y prevenirlo es costoso.

Prevention

Eliminate one of the four conditions, for example by requesting all resources at once or by numbering them and requesting them in order.

Avoidance

Grant a resource only if the system stays in a “safe state” (Dijkstra’s banker’s algorithm).

Detection and recovery

Allow deadlock, detect it with a resource-allocation graph and break it by terminating processes or preempting resources.

Ignore it

The “ostrich algorithm”, used by many general-purpose OSs because deadlock is rare and preventing it is costly.

ConclusionesConclusions

  • La concurrencia mejora el aprovechamiento del sistema, pero el orden de ejecución no es predecible.
  • Cuando los procesos comparten datos, hay que proteger las secciones críticas para evitar condiciones de carrera.
  • Semáforos y monitores son las herramientas habituales; los semáforos bloquean al proceso en lugar de gastar CPU.
  • Sincronizar mal puede producir interbloqueo o inanición, así que conviene diseñar con cuidado el orden de adquisición de recursos.
  • Concurrency improves system utilization, but the execution order is not predictable.
  • When processes share data, critical sections must be protected to avoid race conditions.
  • Semaphores and monitors are the usual tools; semaphores block the process instead of burning CPU.
  • Poor synchronization can cause deadlock or starvation, so the order in which resources are acquired must be designed carefully.
